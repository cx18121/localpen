# Phase 1.5 — Conversational Surface Design

**Status:** Approved (brainstorm complete), ready for implementation planning.
**Date:** 2026-05-27
**Supersedes/extends:** PHASE-1.5-BRIEF.md (this is the real design for the conversational surface; the brief's proactive-nudge "passive AX" concept is explicitly *not* taken — see §9).

## Goal

Extend the Phase 1 quick-action panel into a persistent, multi-turn conversational surface: after a one-shot result, the user can keep refining it in an ongoing thread; threads persist and are resumable. Per ADR 0001, this is the *same panel made stateful*, not a separate chat app. The Phase 1 one-shot loop is preserved unchanged.

## Locked decisions (from brainstorm)

| Decision | Choice |
|---|---|
| Entry into conversation | **Follow-up box** — typing a follow-up under a result promotes it into a thread. Quick-action stays the one-shot default; the fast loop is untouched. |
| Thread layout | **Paired bubbles** — both sides filled, asymmetric, no borders. Localpen = neutral grey (`panelBG2`), left, bottom-left tail; user = faint `accentTint`, right, bottom-right tail. Seeding action renders as a small pill chip, not a sentence. |
| Persistence | **Resumable** — `threads` table + `thread_id` on `interactions`. |
| Resume UX | **Always-available history control** in the panel chrome opens a thread list. |
| Nudges | **In-panel refinement chips** after a result (Soften / Tighten / More formal / More casual). No AX, no out-of-panel observation — stays inside ADR 0003. |
| Architecture | **Dedicated `Conversation` model + `ConversationView`, orchestrated by `PanelController`.** One-shot path unchanged. |
| Turn storage | **Reuse `interactions`** — each turn is an interaction row tagged with `thread_id`; a thread is its rows replayed. DRY, fits ADR 0006. |

### The three confirmed defaults

1. **Conversation system prompt:** a *new* generic "collaboratively refine this text" system prompt frames the thread; the seed action's instruction becomes the first user turn. The seed action's narrow system prompt (e.g. Proofread's) is **not** carried across the thread.
2. **Refinement chips are a fixed set** for v1 — not model-detected. Genuine model-driven nudge detection is deferred.
3. **Thread cleanup is deferred** — persist all threads, show recent ~20 in the list; no expiry policy in v1.

## Components

Each unit has one responsibility and a clear interface.

### `Conversation` (model, `@Observable`)
- **State:** `threadID: Int64`, `originalSelection: Selection`, `turns: [ConversationTurn]`, `operationClass: OperationClass` (inherited from seed action), `streamingText: String` (in-flight reply buffer).
- **`ConversationTurn`:** `{ id: Int64?, role: Role (.user / .assistant), text: String, action: Action? }`. `action` is set on the user turn that was a quick action / chip; nil for free-form follow-ups.
- **Behavior:** append turns; expose the message array for the API (`messages` computed property — see §Prompt assembly); know its `operationClass`.
- **Depends on:** nothing app-specific beyond `Selection` / `Action`.

### `ConversationStore` (persistence)
- **Interface:** `createThread(originalSelection:title:) -> Int64`, `appendTurn(threadID:turn:) async`, `recentThreads(limit:) async -> [ThreadSummary]`, `loadTurns(threadID:) async -> [ConversationTurn]`, `touchThread(threadID:) async` (bump `updated_at`).
- **Implementation:** wraps the existing `Persistence` GRDB `dbQueue`. A turn is persisted as an `Interaction` row with `thread_id` set; `recentThreads` queries the `threads` table ordered by `updated_at desc`.
- **Depends on:** `Persistence`.

### `ConversationView` (SwiftUI)
- Renders the pinned selection context, the paired-bubble thread, refinement chips after the latest assistant turn, the reply box, and per-bubble accept affordances. Observes a `Conversation`.
- **Depends on:** `Conversation`, design tokens, `PanelController` callbacks (submit follow-up, accept turn, tap chip).

### `StreamingClient.complete(messages:sampling:)`
- New entry point taking a full `[(role, content)]` array. The existing `complete(systemPrompt:userText:)` is refactored to build `[system, user]` and delegate to it — single request-building code path.

### `PanelController` (orchestration, existing file)
- Gains `conversation: Conversation?` and `PanelState.Phase.conversing`.
- New responsibilities: `promoteToConversation(followUp:)`, `sendFollowUp(_:)`, `tapChip(_:)`, `acceptTurn(_:)`, `openHistory()`, `resumeThread(_:)`. The one-shot transitions are unchanged.

## State model changes

`PanelState.Phase` gains:
- `case conversing` — show `ConversationView`. The live `Conversation` hangs off `PanelController.conversation` (mirrors how `streamingText` lives outside the enum so per-token updates re-render only the thread).
- `case history` — show the thread list. (Or render history as a sheet/overlay; decided at plan time. The state case is the contract.)

`PanelContext` is unchanged; the conversation carries its own selection/action context.

## Data flow

### Promotion (one-shot result → thread)
1. `.result(text)` is showing; `ConversationView`'s reply box is rendered below the result (the one new affordance in the existing flow — implemented as part of the result view, not a phase change yet).
2. User types a follow-up + Return → `promoteToConversation(followUp:)`:
   - Create `Conversation` with `originalSelection`, `operationClass` = seed action's class, and seed `turns = [ .user(seedAction instruction, action: seedAction), .assistant(resultText) ]`.
   - `threadID = ConversationStore.createThread(...)`; persist the two seed turns.
   - Append `.user(followUp)`.
   - `state = .visible(ctx, .conversing)`; start streaming.

### Turn loop
- `runConversationStream`: `messages = [system] + turns.map(...)`; stream into `conversation.streamingText`; on finish append `.assistant(reply)`, persist it, `touchThread`. Reuses the watchdog machinery; `<500ms` first-token gate dropped.
- Further follow-ups (typed or chip) append a `.user` turn and re-run.

### Accept
- Each assistant bubble has an accept affordance. `acceptTurn(turn)`:
  - revise-class → `textIO.pasteBack` into the source app (existing path).
  - create-class → copy to clipboard (existing `writeToClipboard`).
  - Persist that turn's interaction as `accepted = true`.
- The thread inherits the seed action's class, so accept behavior is consistent across the thread.

### Resume
- `openHistory()` → load `recentThreads`, show list. `resumeThread(id)` → `loadTurns`, rebuild `Conversation`, enter `.conversing`.

## Prompt assembly

- **System:** new `ActionPrompts.conversationSystem` — frames Localpen as collaboratively refining the user's text, with the original selection as standing context. (Appends `styleContext` like other prompts, preserving the Phase-2 voice seam.)
- **Messages:** `system` + for each turn: `{role, content}`. The first user turn's content embeds the seed action instruction + the original selection; subsequent user turns are the raw follow-up text; assistant turns are prior replies.
- This is the multi-turn analog of the existing `ActionPrompts.userMessage`.

## Persistence (migration v2)

```
threads:
  id              INTEGER PK autoincrement
  created_at      INTEGER NOT NULL
  updated_at      INTEGER NOT NULL
  source_app      TEXT
  original_selection TEXT
  title           TEXT          -- derived: original-selection snippet

interactions:
  + thread_id     INTEGER       -- nullable FK to threads.id; NULL for one-shot interactions
```

- One-shot interactions keep `thread_id = NULL` — Phase 1 behavior and existing rows are unaffected.
- Turn order within a thread is by `interactions.timestamp` (already present), tie-broken by `id`.
- Migration is additive (new table + nullable column), so it's a clean GRDB `registerMigration("v2.threads")`.

## Error handling

- A failed turn → an error shown *inside* the conversation (a retry affordance on the failed turn). The thread and prior turns are preserved; never drop the thread on a turn error.
- Reuse `PanelError` and the streaming watchdog. Server-down mid-thread → retry the turn after restart (existing `restartServer` path), thread intact.
- `ConversationStore` write failures are logged and non-fatal (same posture as `Persistence.save` today); a thread that fails to persist still works in-session, it just may not resume.

## Testing (intent, not just behavior)

- **Message assembly** — `Conversation.messages` alternates user/assistant correctly and embeds selection only in the first user turn. *Why:* a malformed role sequence breaks the model's multi-turn understanding.
- **Thread round-trip** — `createThread` → `appendTurn`×N → `loadTurns` returns turns in original order with roles/text intact. *Why:* out-of-order reconstruction corrupts a resumed conversation.
- **operationClass inheritance** — a thread seeded by Respond reports `.create`; accept copies, never pastes back. *Why:* pasting a generated reply over the user's source text is destructive.
- **One-shot isolation** — a one-shot interaction still persists with `thread_id = NULL` and the existing flow is unchanged. *Why:* the daily-use fast loop must not regress.
- **Promotion seeding** — `promoteToConversation` produces `[user(action), assistant(result), user(followUp)]`. *Why:* a dropped seed turn loses the context the follow-up refines.

## Out of scope (YAGNI)

- Model-driven nudge detection ("this reads tense") — v1 chips are a fixed set.
- Thread expiry / cleanup policy — persist all, show recent.
- Out-of-panel / passive AX observation — stays out per ADR 0003.
- Editing or branching past turns; thread export; cross-device sync.
